## 版本更新與付費權限各管一件事

| 機制 | 本次狀態 | 解決的問題 |
| --- | --- | --- |
| 版本檢查、延後提醒、落後三版要求更新 | 納入 v1.1.0 更新流程 | 使用者何時需要升級程式。 |
| 已簽署更新資料、補丁雜湊、備份更新 | 納入 v1.1.0 更新流程 | 下載的補丁是否來自授權發布者及傳輸是否完整。 |
| 帳號／授權碼及訂單管理 | 後續功能 | 誰已購買、可用哪些功能。 |
| 簽署的商業授權憑證、期限與離線寬限 | 後續功能 | 客戶購買的權利如何在程式內表達。 |
| 訂閱付款、退款、發票及客服流程 | 後續營運規劃 | 收費服務如何持續營運。 |

若要販售，先決定是永久使用某一主版本、一定期間內提供更新，還是訂閱服務。永久授權到期通常涉及的是維護或升級資格；是否繼續使用已購買版本，應在購買前明訂。不要把「版本落後」直接當作「未付款」，也不要讓免費更新在沒有清楚說明的情況下把既有功能改成付費才能使用。

## 適合後續加入的設計

1. **獨立的授權服務。** 記錄購買項目、有效期間、可用功能及客戶允許的裝置數；支付卡資料交由付款供應商處理。
2. **簽署的授權憑證。** 程式只內建驗證公鑰，簽發私鑰留在受控服務；不要把可簽發授權的秘密寫進 EXE 或公開 GitHub。
3. **明訂離線政策。** 讓已付費客戶在短暫斷網時仍能工作；是否需要週期性重新驗證、寬限多久，應與產品型態和已承諾條款一致。
4. **分開免費與商業更新通道。** 新增商業通道時採用獨立政策、版本資訊及權限檢查；不能只靠猜得到的下載網址或把金鑰藏在程式裡。
5. **保留可復原的發布流程。** 每次發布保留可重現的原始碼、建置資訊、測試結果、補丁雜湊與變更說明；有問題時發布新的修復序號，不重用舊序號。

即使採用以上設計，也不能保證使用者電腦上的程式無法被修改。本機強制更新有助於版本管理；商業權益還需要授權契約、伺服器端權限與合理的客服流程配合。

## 商業發行前應完成的項目

### Windows 發行者識別

目前作者署名及更新資料簽章，不等同 Windows Authenticode 簽署。正式對外販售時，可評估適合所在地與身分的程式碼簽章服務或憑證，簽署主程式與更新程式。Microsoft 說明 Authenticode 用來驗證發行者與程式完整性；即使有有效簽章，新檔案仍可能因聲譽尚未建立而出現 SmartScreen 提示，不能承諾買憑證就一定不再提示。

- [Microsoft：Authenticode](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/authenticode)
- [Microsoft：Windows 程式碼簽章選項](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)
- [Microsoft：SmartScreen 聲譽](https://learn.microsoft.com/windows/apps/package-and-deploy/smartscreen-reputation)

### 支援的執行環境

程式保留 C# 5／.NET Framework 4.5 API 相容性，不表示應讓客戶使用早已停止維護的 .NET Framework 4.5 runtime。Microsoft 已在 2016-01-12 結束 4.5 的支援。商業版本應建立實際測試矩陣，優先使用仍受支援的 Windows 版本及相容的 .NET Framework 4.8／4.8.1 runtime，並在官網明訂支援範圍。

編譯成功、更新政策測試及介面預覽，不能取代實際 Windows 電腦上的跨版本更新與手機安裝驗證。正式販售前，應在宣稱支援的環境完成包含檔案占用、更新失敗復原及不同裝置的實機驗證，再訂出對客戶承諾的範圍。

- [Microsoft：.NET Framework 生命週期](https://learn.microsoft.com/lifecycle/faq/dotnet-framework)
- [Microsoft：.NET Framework 發行及支援日期](https://learn.microsoft.com/lifecycle/products/microsoft-net-framework)
